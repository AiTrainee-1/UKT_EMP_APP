"Use my password instead". Options are re-read whenever the screen or the
app comes back to the front; a channel switched off meanwhile returns the
screen to the password form.

--------------------------------------------------------------------
One-time code flow (Login, Set Password, Forgot Password)
--------------------------------------------------------------------
Component: src/components/auth/OtpFlow.tsx. Pure rules, wording and tests:
src/lib/otp.ts + src/lib/otp.test.ts. The code is delivered by SMS (2Factor)
or by WhatsApp - HR chooses in the HR portal (SMS Control) - and the server
reports the choice: `otpChannel` on GET /auth/login-options and `channel`
on POST /auth/otp/request. The code's LENGTH follows the channel: 4 digits
by SMS (the approved template says XXXX), 6 on WhatsApp. The server says how
many in `codeLength` (next to `otpChannel` on login-options and `channel` on
otp/request); the field, its label, the "complete" check and the copy all use
that number (src/lib/otp.ts `otpLength`). A server that sends no codeLength
(older): sms 4, whatsapp 6, unknown 6. Endpoints and payloads are otherwise
unchanged (the new key is additive). An app build from before this change only
knows 6 digits, so it cannot sign in with an SMS code until it is updated.

Wording (one table, src/lib/otp.ts `otpCopy`):
  channel 'sms'      "Send code by SMS" / "Code sent by SMS to ••••••1234.
                     It expires in 5 minutes." / "Sign in with an SMS code"
  channel 'whatsapp' "Send code on WhatsApp" / "Code sent to WhatsApp number
                     ••••••1234. It expires in 5 minutes." (as before)
  key missing (an older server) or unknown: neutral - "Send code" /
                     "Code sent to ••••••1234. ..." / "Sign in with a code"
The channel the request answers with wins over the one login-options named.

Step 1 - ask: Employee Code field, a hint line naming the channel and the
  digits ("We will send a 4-digit code by SMS ..."), the send button. A refused request shows the server's own sentence:
    429 + retryAfterSeconds  wait: the button reads "Send code again in 42s"
                             and is disabled until it ends; an "I already
                             have a code" link goes straight to step 2
    429 (hour / number cap), 502 (could not send), 503 (SMS temporarily
    unavailable), 403 (turned off), 400/404/409
                             the sentence, then "Use my password instead"
                             (sign-in only, when the password is on) and the
                             HR contact card ("HR can reset your password
                             for you" / "HR can help you activate your
                             account" on those screens)
    no answer / gateway 5xx  fixed sentence + the software-support card
Step 2 - enter: the notice above (masked number from `maskedPhone`, expiry
  from `expiresInSeconds`), the N-digit field ("4-digit code" by SMS, "6-digit code" on WhatsApp), the submit button, "Change
  employee code", "Resend code in Ns" (countdown from `resendAfterSeconds`,
  clock-based so time spent reading the SMS counts), and "Not getting the
  code? Call HR ..." always visible. When the code's lifetime ends a notice
  says "This code has expired. Please ask for a new one." (the server still
  decides).
Code field: digits only (paste "123 456" works), maxLength = codeLength (4 / 6), numeric
  keypad, textContentType "oneTimeCode", autoComplete "sms-otp" (Android) /
  "one-time-code" (web), importantForAutofill. No auto-submit: the employee
  taps the button. The code is only ever in component state - never logged,
  stored or put in a URL. No new native module is involved, so the keyboard
  suggestion / autofill is the platform's own.

PAGE: Approvals (tab 4 of 5 — MANAGER ONLY)
--------------------------------------------------------------------
Route:    /(tabs)/approvals
File:     app/(tabs)/approvals.tsx
Purpose:  Managers review and approve/reject team requests across
          8 categories.

UI:
  - Gradient header ("Approvals / Review pending requests")
  - Horizontal scroll of per-category stat cards: Leave, Permission,
    Casual Leave*, Attendance*, Missing Punch*, Outpass*, Compensation*,
    Resignations*
    (starred categories only appear if the manager has that specific
    approval capability) — each shows a pending count, tap to switch tab
  - "Compensation" = every compensation claim of the team (one claim table
    since the 19 Nov 2026 backend), raised by the employee or by HR: Sunday /
    holiday work (work date, Sunday / holiday, shifts), OT late-in allowance
    (OT date, shift end, last punch, extra minutes, the allowance minutes), OT
    shift credit (OT times, shifts), birthday credit (1.00 shift) and use of
    the balance (the day off, shifts). Each card has its own type label and a
    "raised by" line (the employee, or the HR user's name); the sheet lists
    the claim's own rows (claimDetailRows), the reason and the raised-on date,
    and a hint saying what approving will do (claimPendingHint: shifts added
    to the balance, the allowance applied on the next working day, the
    shifts taken off the balance for the day off). The approval is final (the
    HOD is the only step); the toast is the server's `effect` sentence
    ("0.75 shift added to Ravi's balance.", "Late-in allowance of 30 min
    applies on 21 Nov."). A refusal (409 claim_refused: payroll month done,
    a day HR set by hand, the balance no longer covers it, HR already paid the
    overtime ...) is shown as the server's sentence. An older backend sends no
    `kind`: every claim there is HR-raised holiday work.
  - FlatList of request cards for the active category: avatar initial,
    employee name/code, type chip, date, reason preview, inline
    Approve/Reject buttons, staggered entrance animation
  - Empty state: "All caught up!"
  - Detail BottomSheet (generic — leave/permission/casualLeave/
    attendance/missingPunch/outpass): full fields + comment TextInput
    + Approve/Reject buttons. Approve needs no comment; Reject needs the
    reason (box relabelled "Reason for rejecting (required)", at least 3
    characters after trimming, src/lib/rejectRemark.ts) - a short reason
    shows "Write the reason for rejecting (at least 3 characters)." under
    the box and sends nothing. The server refuses the same (400
    remark_required); its message is shown in the sheet too
  - Separate detail BottomSheet for resignation: reason, last working
    date, submitted date, survey Q&A, comment, Approve/Reject
  - Toast

Actions:
  - Switch category tab
  - Tap a card or its inline buttons to open the detail sheet (the card's
    Reject opens it already asking for the reason)
  - Approve (comment optional) / Reject (reason required, sent as `comment`)
  - Pull-to-refresh

API calls:
  - useManagerProfile(!!user) -> GET /manager/me
  - usePendingRequests() -> GET /manager/pending-requests
  - useApproveLeave() -> PATCH /manager/leave-requests/{id}/status
  - useApprovePermission() -> PATCH /manager/permissions/{id}/status
  - useResignationAction() -> PATCH /manager/resignations/{id}/action
  - useApproveCasualLeave() -> PATCH /manager/casual-leaves/{id}/status
  - useApproveAttendance() -> PATCH /manager/attendance-requests/{id}/status
  - useApproveMissingPunch() -> PATCH /manager/missing-punch-requests/{id}/status
  - useApproveOutpass() -> PATCH /manager/outpass-requests/{id}/status
  - useApproveHolidayWork() -> PATCH /manager/holiday-work/{id}/status
    body {status, comment}, any claim kind; the reply adds `credited` and
    `effect`. GET /manager/pending-requests carries holidayWorkClaims (every
    kind: kind, kindLabel, raisedByRole, minutes, overtime, useDate), GET
    /manager/me carries canApproveCompensation and pendingCompensationCount
    (every kind; already inside pendingApprovalsCount). Errors
    such as APPROVE_COMPENSATION_DISABLED or "already approved" are shown as
    the server's own sentence; a refusal refreshes the list and the profile.

Conditional/role-gated:
  - The whole tab is hidden from non-managers (href: isManager ?
    undefined : null in the tab layout)
  - Within the screen, Casual Leave / Attendance / Missing Punch /
    Outpass / Compensation / Resignation tabs each only appear if the
    matching manager.canApprove* flag is true (Outpass reuses
    canApprovePermissions; Compensation = canApproveCompensation, absent on
    an older backend = hidden)
  - If the open tab disappears (HR switched the head's approval switch off and
    the profile refetch no longer lists it), the screen falls back to the
    Leave tab instead of an unselected, empty list
  - The tab-bar badge is the sum of the pending counts of the tabs this screen
    shows, every count read from /manager/me: leave + permission, plus casual
    leave / attendance / missing punch / compensation / resignation when that
    tab is listed (src/lib/approvalBadge.ts, which the screen also uses to
    decide the tab list). It is NOT the server's pendingApprovalsCount: that
    total also counts On-Duty requests, and this app has no On-Duty tab, so the
    badge could never be cleared. The Outpass tab is counted from the
    additive pendingOutpassCount key of /manager/me (an older backend without
    it leaves outpass out of the badge). Only an older backend that sends no
    per-kind count falls back to pendingApprovalsCount

6. OFFLINE MODE AND SIGN-IN (NEW 2026-11-24)
====================================================================

Sign-in: lasts until the employee signs out. Each sign-in is a server
session (backend EmployeeLoginSession, 180-day token renewed by POST
/auth/refresh whenever the app is online and the token is older than ~10
days). Sign-out calls POST /auth/logout (best effort) then clears the
phone. Only the server can end a session (401 "Session revoked"); no
internet, timeouts and server errors never sign anyone out.

Offline queue (src/offline): leave, casual leave, permission, missing
punch, outpass, compensation claim / use balance, Enquiries, withdraw, and
On-Duty request / punch (selfies copied into app storage) / end. Each is
sent with an Idempotency-Key (backend api/idempotency.py replays the first
answer, so nothing is created twice). Offline or no answer -> kept in a
SQLite queue on the phone and shown as "Saved on your phone".
Sync: oldest first, at app start, sign-in, foreground, when the internet
comes back, every ~45 s while items wait, and in the background via
expo-background-task (Android WorkManager, >= 15 min, network required).
Only a 2xx removes an item; a refusal stays as "Could not be sent" with
the server's reason (Try again / Delete); 5xx / timeouts retry with
backoff (30 s .. 15 min). Items belong to the employee who made them and
stay on the phone across sign-out.
Status: connection bar (No internet connection. Please turn on your
network to sync your data. / Reconnecting... / Connected / Can't reach the
server), OfflineSyncBar strip, "No internet" popup, /sync page.
Reading offline: React Query cache persisted to AsyncStorage for 3 days
(cleared at sign-out, reset by a new app version).
Native modules added (need a new APK): expo-background-task,
expo-media-library, react-native-view-shot.

- Role gating is centered on three things:
    1. manager.isManager (Approvals tab + its per-category
       canApprove* capability flags)
    2. employee.employmentType === 'production' (drawer's Leave/
       Permissions items hidden for production staff; ID card & My
       Shift layouts differ; weekly schedule differs; the Compensation
       tile / drawer entry / calendar-legend section appear only once the
       profile has said 'staff')
    3. resignation.status (Profile screen's action-card state machine)

- Device-local-only data: the profile photo (useLocalProfilePhoto)
  is intentionally never sent to the server on mobile — it overrides
  the HR-uploaded photo only on that specific device. (The Employee
  Web App's equivalent DOES upload to the server — worth deciding
  whether these should match.)

- Polling intervals worth replicating exactly for a faithful
  recreation:
    Notifications                60 seconds
    Chat messages                4 seconds
    Outpass requests             30 seconds
    Geo-punch status             30 seconds
    On-duty session status       15 seconds
    Manager profile / pending    30 seconds
    Live feed                    20 seconds
    Mobile home summary          60 seconds
